# Codex 正式开发任务书：《灵狐绘卷》局外收藏、图鉴、成就与修行系统

## 一、项目背景和总体任务

当前项目是已经可以运行的《灵狐绘卷》，属于国风剪纸风格的竖屏休闲动作小游戏，计划发布至微信小游戏，并兼顾抖音小游戏的运行环境。

已有玩法包括：

- 小灵狐作为玩家角色，固定在战斗区域中心。
- 玩家通过滑动手指绘制不同符形释放法术。
- 已有直线斩、圆形符、三角形符、雷符等基础技能，具体以当前项目代码为准。
- 符术可以通过局内升级变强，部分具备 Lv4 终极觉醒形态。
- 战斗包含不同妖怪、累计击杀、经验升级、法宝、章节或 Boss 等内容，具体以实际已实现功能为准。
- 游戏目前已经采用 JavaScript / SVG / Path 等方式绘制国风剪纸美术，拥有现成的界面及战斗代码。

本次任务要求：

**一次性在现有项目中开发完成局外长期成长系统，包括万象符录、镇妖功绩、灵狐修行、相关结算入口、存档和完整联动。**

不要只制作 UI 原型，不要只写设计文档，不要分阶段停下等待我确认。

请先检查完整代码，识别现有游戏架构，然后直接实施、接入、测试和修复。

必须保留原有战斗玩法、画符识别、敌人系统、技能动画、已有战斗数值、章节机制及整体美术风格。

禁止重新搭建小游戏项目，禁止为了新增系统而重写整个战斗框架。

# 二、最终系统结构

局外成长统一命名为：

**万象符录**

它是主入口，内部包含以下页面：

1. 符箓收藏：收集、解锁、升级记录、觉醒演出回看。
2. 百妖图鉴：妖怪发现、击杀数量、资料与收藏进度。
3. 山海绘卷：章节发现、通关记录、画卷逐渐补全。
4. 法宝珍藏：法宝发现、获得记录、效果介绍。
5. 镇妖功绩：长期累计、技巧挑战、隐藏成就、奖励领取。
6. 灵狐修行：局外资源、永久解锁、符术与法宝候选池扩展。
7. 游历记录：历史总数据、最佳战绩、最近对局和个人符印。

这七部分必须共用统一的 PlayerProgress 数据系统。

UI 不一定需要七个并排的底部标签。

建议主界面分为：

- 万象符录：首页及收藏内容。
- 镇妖功绩：独立成就页。
- 灵狐修行：独立长期成长页。

万象符录内再用页签进入符箓、妖怪、章节、法宝及游历记录，避免手机端菜单拥挤。

# 三、视觉风格与UI规范

必须继承游戏现有风格：

- 国风剪纸。
- 米白 / 象牙白。
- 朱砂红。
- 暖金。
- 墨黑。
- 山海画卷。
- 云纹、印章、符纸、国风边框。

主视觉参考：

玩家打开收藏界面，如同展开一本古老的山海符录。

不是现代科技面板，也不是简单黑色列表。

可以使用：

- 卷轴展开动画。
- 宣纸背景。
- 朱砂标题。
- 金色细边。
- 深色剪纸卡牌。
- 局部符印装饰。
- 翻页过渡。
- 图鉴盖章解锁效果。

但所有视觉元素都应服从阅读性与手机端操作便利性。

原则：

**美术精致，但界面不要堆满花纹。**

游戏中的大红太阳、远山、梅花枝、古建筑等可以作为装饰语言，但收藏界面以宣纸和书卷为主要背景。

UI需要适配不同竖屏分辨率、安全区域、刘海及底部操作区域。

页面长内容必须支持滚动。

重要按钮点击区域足够大，不允许文字太小难以触摸。

SVG和Canvas渲染应尽量复用已有资源、路径和渲染代码。

# 五、符箓收藏系统

这是整个系统最重要的模块。

## 5.1 符箓基础定义

每个技能在符录内对应一个独立条目。

根据项目中真实存在的符术自动建立或配置图鉴内容。

优先适配这些符形：

- 一字斩。
- 圆形符。
- 三角符。
- 雷符。
- 五角星符。
- 螺旋符。

以上是目标类型，不代表项目已经全部实现。

实际已经存在的技能直接接入。

尚未实现的符术只在有明确设计配置时作为未解锁条目出现，不得生成假的战斗行为。

每个符术具有：

- 唯一 spellId。
- 显示名称。
- 所属派系。
- 描述。
- 手势类型。
- 四级形态定义。
- 当前收藏状态。
- 最高达到等级。
- 历史施法次数。
- 累计命中次数。
- 累计伤害。
- 累计击杀。
- 单次最高伤害。
- 首次发现时间。
- 首次觉醒时间。
- 是否可回看终极动画。

## 5.2 符箓收藏状态

每个技能支持四类收藏状态：

UNSEEN：未发现。
DISCOVERED：已经发现。
MASTERED：已经达到普通最高等级。
AWAKENED：曾在战斗中完成 Lv4 觉醒。

这四类状态不可只凭数值推断，应依据实际事件更新，并能根据历史最高等级正确恢复。

当一个符术首次成功释放时：

- 设置为已发现。
- 写入首次发现时间。
- 触发一次图鉴解锁提示。

当玩家在某局达到 Lv3：

- 记录已精通。
- 解锁普通三级符术展示。

当玩家在某局达到 Lv4：

- 记录已觉醒。
- 保存首次觉醒时间。
- 解锁对应终极技能演出回放。
- 触发专属觉醒收藏提示。

图鉴解锁不意味着下一局自动获得高等级技能。

## 5.3 符箓展示卡

符箓列表采用卡牌展示。

每张卡片应有：

- 技能图案。
- 技能名称。
- 所属派系。
- 收藏状态。
- 最高等级。
- 特殊等级边框。

推荐：

未发现：暗色剪影。

已发现：米白符纸卡。

已精通：红金边框。

已觉醒：金色印章及专属装饰。

不要大面积使用动态粒子，以免低端手机掉帧。

## 5.4 符箓详情页

点击某个技能后，进入符箓详情。

需要包括：

A. 大型符箓主视觉。

B. 四级技能展示区：

- Lv1。
- Lv2。
- Lv3。
- Lv4。

已解锁等级可以查看介绍与视觉。

未解锁等级显示剪影和简要提示。

C. 符术介绍。

D. 历史记录：

- 总施法次数。
- 总伤害。
- 总击杀。
- 单次最高伤害。
- 历史最高等级。
- 首次觉醒时间。

E. 技能演出预览按钮。

## 5.5 终极技能回放

如果技能已经 Lv4 觉醒，解锁演出回放按钮。

必须尽可能复用当前游戏已经实现的技能 VFX 模块，而不是复制一份完全不同的演出逻辑。

如果现有战斗模块不能直接在局外使用，则制作一个小型独立特效预览容器，接入同一套技能视觉组件。

回放界面应支持：

- 播放。
- 重新播放。
- 关闭。
- 返回图鉴。

背景可采用简化的深色剪纸场景。

不得直接开启一局完整战斗才能观看动画。

演出中不应真实扣血、刷怪或改变存档。

没有实现 Lv4 VFX 的符术，不允许假装有完整终极动画；显示尚未开放或使用明确的静态展示。

## 5.6 个人符印

每种符箓可以记录玩家第一次成功释放时的手绘轨迹。

注意：不要直接存储完整原始触屏事件流。

建议对绘制轨迹进行：

- 去抖。
- 采样。
- 简化。
- 归一化。
- 点数量限制。

建议每个符术最多保留 32～64 个归一化轨迹点。

存档时只保存必要的数据。

符箓详情中可以展示这一笔迹，并附文字：

“初绘符痕”。

如果现有手势识别模块无法稳定提供轨迹，则增加兼容适配层，不要破坏原有识别逻辑。

# 六、百妖图鉴

## 6.1 基本设计

所有已存在的敌人类型均应接入百妖图鉴。

以真实 enemyTypeId 作为唯一标识。

不能依靠显示名称匹配怪物。

每种妖怪记录：

- enemyTypeId。
- 名称。
- 类型。
- 简介。
- 首次遇见时间。
- 首次击杀时间。
- 累计击杀数量。
- 首次击杀所在章节。
- 该妖怪最高单局击杀数量。
- 已解锁资料等级。

## 6.2 解锁过程

初次遇见：

显示剪影及基础名称。

首次击败：

解锁完整剪纸立绘与基础介绍。

累计击杀达到一定数量：

解锁进一步的传闻或弱点提示。

例如：

首次击杀：解锁基础资料。

累计10次：解锁妖怪习性。

累计50次：解锁妖怪传闻。

累计200次：获得图鉴印章。

以上阈值可配置。

资料和传闻要由配置提供，不要让程序随机生成没有设定依据的世界观文案。

## 6.3 妖怪图鉴视觉

建议设计为：

左侧妖怪剪纸立绘。

右侧名称、类别、传闻。

底部历史击杀数量及解锁进度。

精英与 Boss 可以拥有不同颜色的印章边框。

当妖怪尚未解锁时显示暗色剪影，不允许泄露完整图片。

# 七、山海绘卷系统

这部分要与游戏名称《灵狐绘卷》形成明显关联。

## 7.1 一章一卷

每个实际存在的战斗章节，对应一幅山海绘卷。

目标世界观可包含：

- 落日妖谷。
- 幽篁竹海。
- 血月妖祠。
- 星河天宫。

具体必须根据现有章节代码核对。

尚不存在的章节可以保留数据定义与锁定入口，但不得显示为已开放。

## 7.2 每幅绘卷的成长状态

LOCKED：未发现。

DISCOVERED：进入过该章节。

CLEARED：完成章节。

MASTERED：完成章节指定挑战。

对应画卷展示为：

未发现：折起的暗色画卷。

已发现：画卷展开一部分，显示基础山峦和天空。

已通关：完整展开，显示完整场景。

已精通：画卷上出现朱砂题款及金色成就印章。

## 7.3 章节记录

记录：

- 首次进入时间。
- 进入次数。
- 通关次数。
- 最快通关时间。
- 最高分数。
- 最高连杀。
- 完成的特殊挑战。
- 当前绘卷收藏等级。

## 7.4 视觉与动画

山海绘卷不要只是一个简单进度条。

应复用当前游戏的背景美术元素：

- 层叠山峦。
- 朱红落日。
- 竹林。
- 远景建筑。
- 云海。
- 特殊章节符纹。

已解锁部分逐渐显示。

如果是 SVG 实现，可使用 mask、clipPath、Path 渐显及简单卷轴展开动画。

打开一幅画卷时：

- 卷轴缓慢展开。
- 山海景物依次显露。
- 通关印章最后落下。

动画要短、流畅，支持跳过，避免反复打开造成等待。

# 八、法宝珍藏

法宝收藏和符箓收藏应分开。

符箓代表玩家施展的技能。

法宝代表改变战斗构筑的道具与能力。

## 8.1 基础字段

每件法宝记录：

- itemId。
- 名称。
- 稀有度。
- 效果说明。
- 图鉴插画或图标。
- 是否发现。
- 首次获得时间。
- 累计获得次数。
- 使用次数。
- 最高单局获得数量。

## 8.2 收集规则

首次获得：

解锁图鉴条目。

累计获得一定次数：

解锁法宝铭文、故事或收藏印章。

法宝的永久发现状态不得直接等同于当前局内持有状态。

## 8.3 法宝组合提示

当玩家获得过两件能够形成指定组合的法宝后，可以在图鉴中解锁“组合秘闻”。

例如：

朱砂灵笔 + 某类多段符术：展示可能的连锁效果。

照妖古镜 + 特定防御符术：展示反击搭配建议。

具体组合必须根据真实存在的法宝及实际规则配置。

不要为了图鉴介绍临时添加未经过设计的新战斗机制。

# 九、镇妖功绩系统

镇妖功绩是永久累计成就系统。

必须由实际的 GameplayEvent 驱动，不允许 UI 自己随意修改成就进度。

## 9.1 三大类型

ACCUMULATION：长期累计。

CHALLENGE：技巧挑战。

HIDDEN：隐藏奇遇。

每个成就具备：

- achievementId。
- 名称。
- 描述。
- 分类。
- 目标。
- 当前进度。
- 完成时间。
- 是否已完成。
- 是否已领奖。
- 奖励内容。
- 是否隐藏。
- 前置条件。

## 9.2 首版实现24项成就

# 十、灵狐修行系统

这是永久成长模块。

但必须避免局外成长破坏游戏的肉鸽随机性。

## 10.1 设计原则

永久成长优先解锁：

- 新技能进入随机候选池。
- 新法宝进入随机候选池。
- 新的开局选择。
- 个性化外观。
- 收藏内容。
- 极少量可控的初始资源便利性。

不允许直接通过修行把所有技能永久升级至Lv4。

不允许大幅堆叠永久伤害，导致后续关卡失去挑战性。

## 10.2 资源

优先复用项目已有的局外资源。

如果没有合适的资源，则增加一种统一资源：

朱砂。

朱砂来源：

- 对局结束奖励。
- 章节首次通关。
- 成就领奖。
- 收藏里程碑奖励。

具体获得公式可配置。

避免多种永久货币在首版同时出现。

## 10.3 修行路线

首版建议设置三条分支：

### 符道

解锁新的可选符术。

解锁特殊绘符样式。

解锁更丰富的符术构筑选择。

### 法宝

解锁新的法宝进入局内奖励池。

解锁法宝组合记录。

解锁部分开局法宝选择资格。

### 灵狐

解锁角色装饰。

解锁法阵配色。

解锁符纸外观。

解锁个人符印展示。

所有内容以配置形式定义。

对于未实现的真实内容，必须检查资源是否已经存在。

没有内容时应保持锁定，不允许生成无法生效的按钮。

## 10.4 修行购买逻辑

每个修行节点具有：

- unlockId。
- 名称。
- 描述。
- 所属分支。
- 消耗。
- 前置节点。
- 效果类型。
- 是否已解锁。

购买时：

1. 检查前置条件。
2. 检查货币余额。
3. 原子性扣除货币并记录解锁。
4. 立即刷新展示。
5. 后续对局读取解锁状态。

不允许重复购买同一不可重复节点。

解锁外观后提供装备 / 取消装备功能。

默认外观应始终可用。

# 十二、统一事件系统与统计接入

这是最关键的底层要求。

禁止各个图鉴和成就页面分别监听自己的临时游戏数据。

应增加或复用统一的 GameplayEvent / ProgressEvent 系统。

建议至少支持以下语义事件：

- RUN_STARTED
- RUN_ENDED
- SPELL_CAST_SUCCESS
- SPELL_HIT
- SPELL_DAMAGE
- SPELL_LEVEL_UP
- SPELL_AWAKENED
- ENEMY_SEEN
- ENEMY_KILLED
- BOSS_DEFEATED
- ITEM_ACQUIRED
- CHAPTER_ENTERED
- CHAPTER_CLEARED
- PLAYER_DAMAGED
- SPECIAL_EVENT_COMPLETED

事件名称可以根据现有代码命名，但语义必须明确。

每个事件包含必要的：

- eventId。
- runId。
- timestamp。
- eventType。
- payload。

需要正确识别：

- 施法成功不等于触摸开始。
- 技能命中不等于技能释放。
- 一次技能命中多个敌人应按不同 enemyInstanceId 聚合。
- 同一敌人死亡不能重复计数。
- 技能升级事件不能重复触发觉醒收藏。
- 章节完成只能按实际通关逻辑触发。
- 领取成就奖励不能重复执行。

请建立 ProgressTracker 或等效模块，从事件更新玩家永久数据。

成就判断和图鉴更新使用同一套统计结果。

# 十四、存档与微信小游戏兼容

这是准备上线微信小游戏的项目。

不得假设始终存在浏览器 localStorage、document、window 或完整 DOM。

请优先检查现有游戏的运行时适配层。

使用统一 StorageAdapter。

推荐：

微信小游戏环境：

使用 wx.getStorageSync / wx.setStorageSync，或项目已实现的适配方式。

Web开发环境：

可以使用 localStorage 等已有存储方案。

抖音小游戏环境：

通过单独适配器支持对应平台存储API，不要将微信接口硬编码进业务层。

## 14.1 存档要求

需要做到：

- 首次进入创建存档。
- 重启游戏恢复存档。
- 断局后保存已经确认的永久事件。
- 结算时保存完整本局结果。
- 防止重复结算。
- 支持旧存档迁移。
- 处理损坏JSON。
- 处理存储失败。
- 保存失败时不能显示虚假的保存成功提示。

建议采用：

版本号。
运行中状态。
稳定持久化数据。
幂等事件处理。
必要的检查点保存。

不要每产生一个粒子或每击中一次敌人就同步写入整个存档。

在安全检查点或合理节流后保存。

对于成就领奖、货币扣除、永久解锁等关键操作，需要确保状态一致性。

## 14.2 不允许伪造历史记录

项目如果以前没有统计某项数据，不能把过去的历史数据编造出来。

可以从首次接入该系统开始累计。

若现有存档已经具备历史记录，则根据可靠字段迁移。
